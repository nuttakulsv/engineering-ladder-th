| L5 | Principal Engineer | ทั้งองค์กร | กำหนดทิศทางเทคนิคขององค์กรในระยะหลายปี การตัดสินใจส่งผลต่อรายได้ ต้นทุน หรือความเสี่ยงของบริษัทโดยตรง |

## L1 Junior Engineer

ทำงานที่ถูกแบ่งมาแล้วได้สำเร็จโดยมีคนคอยแนะนำ กำลังเรียนรู้ระบบ เครื่องมือ และวิธีทำงานของทีม

ขอบเขต: งานย่อยที่มีคนแบ่งมาให้แล้ว

### L1 · ทักษะทางเทคนิค

**สิ่งที่เห็นได้ในงานจริง**

- เขียนโค้ดที่ทำงานถูกต้องตาม task ที่ได้รับ และเขียน test ตามแบบที่ทีมใช้อยู่
- อ่านโค้ดเดิมของทีมเพื่อหาว่าต้องแก้ตรงไหนก่อนจะถามคนอื่น
- ใช้เครื่องมือหลักของทีมได้เอง เช่น git, debugger, log และรันโปรเจกต์บนเครื่องตัวเองได้

**ยังไม่ถึงระดับนี้ ถ้า**

- ยังต้องมีคนนั่งข้าง ๆ ทุกครั้งที่ต้องรันโปรเจกต์หรือแก้ conflict ใน git

**หลักฐานที่ใช้ตอนประเมิน**

- PR ที่ merge แล้วพร้อม test
- จำนวนรอบ review ต่อ PR ที่ลดลงในช่วง 3 เดือน

**ถ้าอยากไปถึง**

- ขอให้รุ่นพี่ review แบบอธิบายเหตุผล ไม่ใช่แค่บอกให้แก้ แล้วจดเรื่องที่โดนทักซ้ำไว้ทบทวน

### L1 · การส่งมอบงาน

**สิ่งที่เห็นได้ในงานจริง**

- แบ่ง task ที่ได้รับเป็นขั้นเล็ก ๆ และบอกได้ว่าวันนี้ทำถึงไหน
- ถามเมื่อติดนานเกินกว่าที่ทีมตกลงกันไว้ ไม่เงียบหาย
- ปิดงานให้ครบตาม definition of done ของทีม รวม test และการอัปเดต ticket

**ยังไม่ถึงระดับนี้ ถ้า**

- ติดปัญหาเป็นวันโดยไม่มีใครรู้
- บอกว่าเสร็จแล้ว แต่ยังไม่ได้ลองใช้งานจริงเลย

**หลักฐานที่ใช้ตอนประเมิน**

- ข้อความใน standup หรือ chat ที่แจ้งปัญหาก่อนเลยกำหนด

**ถ้าอยากไปถึง**

- ตั้งเวลาให้ตัวเอง ถ้าติดเกิน 2 ชั่วโมงให้เขียนสรุปสิ่งที่ลองไปแล้วส่งถามในทีม

### L1 · ขอบเขตและผลกระทบ

**สิ่งที่เห็นได้ในงานจริง**

- ทำงานในขอบเขต task หรือ bug ที่มีคนแบ่งมาให้ และทำได้ครบตามขอบเขตนั้น
- อธิบายได้ว่า task ที่ทำอยู่ช่วยผู้ใช้หรือธุรกิจตรงไหน
- เสนอการปรับปรุงเล็ก ๆ ที่เจอระหว่างทำงาน เช่น error message ที่อ่านไม่รู้เรื่อง หรือเอกสารที่ล้าสมัย

**ยังไม่ถึงระดับนี้ ถ้า**

- ทำตาม spec ตรงตัวอักษร ทั้งที่เห็นว่าผลลัพธ์ไม่ตอบโจทย์ผู้ใช้ และไม่ถามใคร

**หลักฐานที่ใช้ตอนประเมิน**

- ticket หรือ PR เล็ก ๆ ที่เปิดเองจากสิ่งที่เจอระหว่างทำงาน

**ถ้าอยากไปถึง**

- ก่อนเริ่ม task ให้ถามตัวเองว่าใครจะใช้สิ่งนี้ และเขาจะรู้ได้ยังไงว่ามันใช้ได้

### L1 · การทำงานร่วมกันและการสื่อสาร

**สิ่งที่เห็นได้ในงานจริง**

- เขียน PR description ที่บอกว่าแก้อะไร ทำไม และทดสอบยังไง
- รับ feedback ใน code review โดยไม่ถือเป็นเรื่องส่วนตัว และตอบทุกคอมเมนต์
- เวลาถามให้ข้อมูลครบ: ทำอะไรอยู่ คาดว่าจะได้อะไร ได้อะไรจริง และลองอะไรไปแล้ว

**ยังไม่ถึงระดับนี้ ถ้า**

- ถามว่า 'มันไม่ทำงานครับ' โดยไม่มีบริบท
- กด resolve คอมเมนต์ใน review โดยไม่ได้แก้และไม่ได้ตอบ

**หลักฐานที่ใช้ตอนประเมิน**

- PR description และคำถามใน channel ของทีม

**ถ้าอยากไปถึง**

- ใช้คำถามสี่ข้อข้างบนทุกครั้งที่ถาม จนเป็นนิสัย

### L1 · การพัฒนาคนและภาวะผู้นำ

**สิ่งที่เห็นได้ในงานจริง**

- ช่วยตอบคำถามคนที่เข้ามาใหม่กว่า ในเรื่องที่ตัวเองเพิ่งเรียนรู้มา
- แก้หรือเพิ่มเอกสาร onboarding เมื่อเจอว่ามันผิดหรือขาด
- บอกหัวหน้าได้ว่าอยากพัฒนาเรื่องอะไรต่อ

**ยังไม่ถึงระดับนี้ ถ้า**

- รอให้คนอื่นบอกตลอดว่าต้องเรียนอะไร

**หลักฐานที่ใช้ตอนประเมิน**

- PR ที่แก้เอกสาร onboarding
- เป้าหมายการพัฒนาที่คุยไว้ใน 1:1

**ถ้าอยากไปถึง**

- หลังเข้าใจเรื่องไหนแล้ว ลองอธิบายให้เพื่อนในทีมฟัง หรือเขียนโน้ตสั้น ๆ ลง wiki

### L1 · ความเป็นเจ้าของและมุมมองธุรกิจ

**สิ่งที่เห็นได้ในงานจริง**

- รู้ว่างานของตัวเองขึ้น production เมื่อไหร่ และตามดูหลัง deploy ว่าใช้งานได้จริง
- ยอมรับเมื่อทำพลาด และแจ้งทันทีพร้อมข้อมูลที่รู้
- ทำตามกระบวนการเรื่องความปลอดภัยและข้อมูลลูกค้าของทีมเสมอ แม้ตอนรีบ

**ยังไม่ถึงระดับนี้ ถ้า**

- ปิด ticket แล้วไม่สนใจว่าใช้ได้จริงไหม
- ปิดบังความผิดพลาดจนคนอื่นมาเจอเอง

**หลักฐานที่ใช้ตอนประเมิน**

- ข้อความแจ้งปัญหาหลัง deploy ที่ตัวเองเป็นคนเจอก่อน

**ถ้าอยากไปถึง**

- หลัง deploy ทุกครั้ง เปิด log หรือ dashboard ดูสัก 10 นาที

## L2 Engineer

ทำ feature ได้เองตั้งแต่ต้นจนจบ ต้องการคำแนะนำเฉพาะเรื่องที่ใหม่หรือเสี่ยง เป็นกำลังหลักของทีม

ขอบเขต: feature

### L2 · ทักษะทางเทคนิค

**สิ่งที่เห็นได้ในงานจริง**

- ออกแบบและทำ feature ขนาดกลางได้เอง เลือกวิธีที่เข้ากับโค้ดเดิมโดยไม่ต้องมีคนบอก
- เขียน test ที่จับ bug ได้จริง เลือกได้ว่าเมื่อไหร่ควรเป็น unit และเมื่อไหร่ควรเป็น integration
- debug ปัญหาใน production จาก log และ metric ได้เองในส่วนที่ทีมดูแล

**ยังไม่ถึงระดับนี้ ถ้า**

- ทุก feature ยังต้องมีคนออกแบบให้ก่อน
- fix ที่ส่งขึ้นไปแก้แค่อาการ แล้วปัญหาเดิมกลับมาอีก

**หลักฐานที่ใช้ตอนประเมิน**

- feature ที่ออกแบบเองพร้อม test
- บันทึกการ debug incident เล็ก ๆ

**ถ้าอยากไปถึง**

- ก่อนเริ่ม feature ถัดไป เขียนแผนครึ่งหน้าให้ senior อ่านก่อนลงมือ

### L2 · การส่งมอบงาน

**สิ่งที่เห็นได้ในงานจริง**

- ประมาณเวลางานระดับ feature ได้ใกล้เคียง และบอกล่วงหน้าเมื่อรู้ว่าจะช้า
- แบ่ง feature เป็น PR เล็ก ๆ ที่ review ได้ในไม่กี่สิบนาที และ merge ได้ทีละส่วน
- จัดลำดับงานของตัวเองได้เมื่อมีงานแทรก และบอกได้ว่าอะไรจะเลื่อนออกไป

**ยังไม่ถึงระดับนี้ ถ้า**

- เปิด PR ใหญ่หลายพันบรรทัดที่ไม่มีใครกล้า review
- รู้ว่าจะช้าแต่มาบอกในวันส่ง

**หลักฐานที่ใช้ตอนประเมิน**

- ขนาด PR และระยะเวลารอ review
- ข้อความแจ้งเลื่อนก่อนถึงกำหนด

**ถ้าอยากไปถึง**

- ใช้ feature flag หรือแยก PR ตามชั้นของงาน เช่น schema, logic, UI เพื่อให้ merge ได้เร็ว

### L2 · ขอบเขตและผลกระทบ

**สิ่งที่เห็นได้ในงานจริง**

- รับผิดชอบ feature หนึ่งตั้งแต่ต้นจนจบ รวมถึงการคุยกับ product หรือ designer
- ชี้ได้ว่า requirement ไหนยังไม่ชัด และถามก่อนลงมือ
- ทิ้งโค้ดส่วนที่แก้ให้ดีขึ้นกว่าตอนเจอเล็กน้อยทุกครั้ง ภายในขอบเขตงานเดิม

**ยังไม่ถึงระดับนี้ ถ้า**

- มองว่างานจบที่ 'โค้ดเสร็จ' โดยไม่สนว่า feature ถูกใช้หรือไม่

**หลักฐานที่ใช้ตอนประเมิน**

- feature ที่ส่งมอบแล้วมีคนใช้ หรือ metric ที่ดีขึ้นหลังปล่อย

**ถ้าอยากไปถึง**

- ขอดูข้อมูลการใช้งานของ feature ที่ทำ หลังปล่อยไปแล้ว 2 สัปดาห์

### L2 · การทำงานร่วมกันและการสื่อสาร

**สิ่งที่เห็นได้ในงานจริง**

- review โค้ดของคนอื่นอย่างมีสาระ ชี้ปัญหาจริง และแยกเรื่องสำคัญออกจากความชอบส่วนตัว
- อธิบายเรื่องเทคนิคให้ product หรือ QA เข้าใจได้โดยไม่ใช้ศัพท์เกินจำเป็น
- ติดต่อคนนอกทีมเพื่อปลด blocker ของตัวเองได้

**ยังไม่ถึงระดับนี้ ถ้า**

- approve PR โดยไม่ได้อ่าน หรือคอมเมนต์แค่เรื่องจัดรูปแบบโค้ด

**หลักฐานที่ใช้ตอนประเมิน**

- คอมเมนต์ใน code review ที่ช่วยกันปัญหาได้จริง

**ถ้าอยากไปถึง**

- เวลา review ให้ใส่คำนำหน้าคอมเมนต์ เช่น 'ต้องแก้:' กับ 'ข้อเสนอ:' ให้คนอ่านรู้ว่าเรื่องไหนบังคับ

### L2 · การพัฒนาคนและภาวะผู้นำ

**สิ่งที่เห็นได้ในงานจริง**

- เป็น buddy ให้คนใหม่ในช่วง onboarding ได้
- แชร์สิ่งที่เรียนรู้ให้ทีม เช่น สรุปปัญหาที่เจอ หรือเทคนิคที่ช่วยประหยัดเวลา
- ขอ feedback จากคนรอบตัวเป็นประจำ ไม่รอรอบประเมิน

**ยังไม่ถึงระดับนี้ ถ้า**

- ช่วยคนอื่นเฉพาะตอนถูกขอ และความรู้ที่มีอยู่แค่ในหัวตัวเอง

**หลักฐานที่ใช้ตอนประเมิน**

- คนใหม่ที่ดูแลส่งงานแรกได้ภายในเวลาที่ทีมตั้งไว้

**ถ้าอยากไปถึง**

- อาสาเป็น buddy ให้คนเข้าใหม่คนถัดไป

### L2 · ความเป็นเจ้าของและมุมมองธุรกิจ

**สิ่งที่เห็นได้ในงานจริง**

- ดูแลส่วนที่ตัวเองสร้างหลังปล่อยแล้ว ทั้งแก้ bug และตอบคำถามเกี่ยวกับมัน
- อยู่เวร on-call ของทีมได้ และรู้ว่าต้องทำอะไรเมื่อเกิดเหตุ
- เห็นความเสี่ยงด้านความปลอดภัยหรือข้อมูลส่วนบุคคลในงานของตัวเอง และยกขึ้นมาคุย

**ยังไม่ถึงระดับนี้ ถ้า**

- ส่งต่อปัญหาให้คนอื่น ทั้งที่เป็นส่วนที่ตัวเองทำ

**หลักฐานที่ใช้ตอนประเมิน**

- การอยู่เวร on-call และ postmortem ที่มีส่วนร่วม

**ถ้าอยากไปถึง**

- เขียน runbook สั้น ๆ สำหรับ feature ที่ตัวเองดูแล

## L3 Senior Engineer

รับโจทย์ที่ยังไม่ชัดแล้วทำให้ชัด นำโปรเจกต์ของทีมจนสำเร็จ และทำให้คนรอบตัวทำงานดีขึ้น ไม่ใช่แค่ทำงานตัวเองเก่ง

ขอบเขต: โปรเจกต์หรือส่วนของระบบที่ทีมดูแล

### L3 · ทักษะทางเทคนิค

**สิ่งที่เห็นได้ในงานจริง**

- ออกแบบระบบหรือส่วนประกอบใหม่ที่หลายคนจะทำงานต่อ และเขียน design doc ให้คนอื่นวิจารณ์ได้
- เทียบ trade-off ของแต่ละทางเลือก เช่น ความเร็ว ต้นทุน ความซับซ้อน การดูแลรักษา และอธิบายได้ว่าทำไมเลือกทางนี้
- ยกระดับคุณภาพงานของทั้งทีม เช่น ปรับ CI ทำเครื่องมือ หรือวางมาตรฐาน test ที่คนอื่นใช้ตาม

**ยังไม่ถึงระดับนี้ ถ้า**

- เก่งเฉพาะงานตัวเอง แต่ทีมไม่ได้ทำงานดีขึ้นเพราะเขา
- เลือกเทคโนโลยีจากความชอบ โดยไม่มีเหตุผลที่เอามาเทียบกันได้

**หลักฐานที่ใช้ตอนประเมิน**

- design doc ที่ถูกใช้จริง
- การเปลี่ยนแปลงที่ทำให้ build หรือ deploy ของทีมเร็วขึ้น

**ถ้าอยากไปถึง**

- เขียน design doc ของงานถัดไปพร้อมทางเลือกอย่างน้อยสองทาง แล้วให้คนในทีมวิจารณ์

### L3 · การส่งมอบงาน

**สิ่งที่เห็นได้ในงานจริง**

- นำโปรเจกต์ที่กินเวลาหลายสัปดาห์และมีคนร่วมทำ 2–4 คนจนสำเร็จ
- เห็นความเสี่ยงของโปรเจกต์ตั้งแต่ต้น และทำส่วนที่ยากหรือไม่แน่นอนที่สุดก่อน
- ตัดขอบเขตงานอย่างมีเหตุผลเมื่อเวลาไม่พอ โดยตกลงกับ product ไม่ใช่ตัดเงียบ ๆ

**ยังไม่ถึงระดับนี้ ถ้า**

- โปรเจกต์ที่นำเลื่อนบ่อย และคนอื่นรู้ทีหลัง
- ทำส่วนง่ายก่อน แล้วไปเจอปัญหาใหญ่ตอนท้าย

**หลักฐานที่ใช้ตอนประเมิน**

- โปรเจกต์ที่นำ พร้อมไทม์ไลน์และการตัดสินใจระหว่างทาง

**ถ้าอยากไปถึง**

- ในโปรเจกต์ถัดไป เขียนความเสี่ยง 3 อันดับแรกตั้งแต่สัปดาห์แรก และทบทวนทุกสัปดาห์

### L3 · ขอบเขตและผลกระทบ

**สิ่งที่เห็นได้ในงานจริง**

- ขอบเขตงานคือโปรเจกต์หรือส่วนของระบบที่ทีมดูแล ไม่ใช่แค่ feature
- รับโจทย์ที่ยังไม่ชัด แล้วทำให้ชัดพอที่ทีมจะลงมือได้
- งานที่ทำเปลี่ยนตัวเลขที่ทีมหรือธุรกิจสนใจ และวัดผลได้

**ยังไม่ถึงระดับนี้ ถ้า**

- รอให้มีคนแปลงโจทย์เป็น ticket ให้ก่อนเสมอ

**หลักฐานที่ใช้ตอนประเมิน**

- โจทย์คลุมเครือที่ถูกแปลงเป็นแผนงานโดยคนนี้
- ตัวเลขก่อนและหลังโปรเจกต์

**ถ้าอยากไปถึง**

- ขอรับโจทย์ระดับปัญหา เช่น 'ลดการชำระเงินที่ล้มเหลว' แทนโจทย์ระดับ ticket

### L3 · การทำงานร่วมกันและการสื่อสาร

**สิ่งที่เห็นได้ในงานจริง**

- ช่วยให้ทีมตัดสินใจเรื่องเทคนิคได้ แม้คนในทีมเห็นต่างกัน โดยไม่ต้องรอให้คนที่อาวุโสที่สุดชี้ขาด
- บอกทีมอื่นล่วงหน้าเรื่อง API, dependency และการเปลี่ยนแปลงที่กระทบเขา
- เขียนเอกสารที่คนนอกทีมอ่านแล้วใช้งานได้โดยไม่ต้องถามต่อ

**ยังไม่ถึงระดับนี้ ถ้า**

- ชนะการถกเถียง แต่ทีมไม่เดินต่อ
- เปลี่ยน API ที่ทีมอื่นใช้โดยไม่บอกก่อน

**หลักฐานที่ใช้ตอนประเมิน**

- บันทึกการตัดสินใจ (ADR) ที่มีคนเห็นต่างแต่ยอมรับเหตุผล

**ถ้าอยากไปถึง**

- ในประชุมถัดไปที่มีความเห็นต่าง ให้สรุปข้อดีของฝั่งที่ตัวเองไม่เห็นด้วยก่อน แล้วค่อยเสนอความเห็นตัวเอง

### L3 · การพัฒนาคนและภาวะผู้นำ

**สิ่งที่เห็นได้ในงานจริง**

- mentor คนในทีมอย่างต่อเนื่อง จนเขารับงานที่ใหญ่ขึ้นได้
- review โค้ดแบบอธิบายเหตุผล ให้คนที่ถูก review เก่งขึ้น ไม่ใช่แค่โค้ดดีขึ้น
- มีส่วนในการสัมภาษณ์และ onboarding คนเข้าใหม่

**ยังไม่ถึงระดับนี้ ถ้า**

- ทำงานยากเองทั้งหมดเพราะทำได้เร็วกว่า ทำให้คนอื่นในทีมไม่ได้โต

**หลักฐานที่ใช้ตอนประเมิน**

- คนที่ mentor ได้เลื่อนระดับหรือรับงานใหญ่ขึ้น
- scorecard การสัมภาษณ์ที่เขียนชัดเจน

**ถ้าอยากไปถึง**

- ยกงานที่ตัวเองทำได้เร็วที่สุดหนึ่งชิ้นให้คนอื่นทำ แล้วเปลี่ยนตัวเองเป็นคนคอยช่วย

### L3 · ความเป็นเจ้าของและมุมมองธุรกิจ

**สิ่งที่เห็นได้ในงานจริง**

- เป็นเจ้าของคุณภาพของระบบที่ทีมดูแล ทั้ง alert ความพร้อมใช้งาน และหนี้ทางเทคนิค
- นำการแก้ incident และเขียน postmortem ที่นำไปสู่การแก้ต้นเหตุ
- บาลานซ์งานใหม่กับการลดหนี้ทางเทคนิค และอธิบายให้ product เข้าใจได้ว่าทำไม

**ยังไม่ถึงระดับนี้ ถ้า**

- รู้ว่าระบบมีจุดเสี่ยงแต่ไม่ได้ยกขึ้นมา
- ขอเวลาแก้หนี้ทางเทคนิคโดยอธิบายผลกระทบไม่ได้

**หลักฐานที่ใช้ตอนประเมิน**

- postmortem ที่เขียน และ action item ที่ปิดได้จริง

**ถ้าอยากไปถึง**

- ทำรายการหนี้ทางเทคนิค 5 อันดับแรกของทีมพร้อมผลกระทบที่วัดได้ แล้วเอาไปคุยกับ product

## L4 Staff Engineer / Tech Lead

กำหนดทิศทางเทคนิคของทีมหรือหลายทีม หาปัญหาที่สำคัญที่สุดเอง และพาคนอื่นไปแก้ ผลงานวัดจากสิ่งที่ทีมทำได้ ไม่ใช่โค้ดที่เขียนเอง

ขอบเขต: ทั้งทีมหรือหลายทีม

### L4 · ทักษะทางเทคนิค

**สิ่งที่เห็นได้ในงานจริง**

- กำหนดทิศทางเทคนิคของทีมหรือหลายทีม เช่น สถาปัตยกรรม มาตรฐาน และเทคโนโลยีหลัก ที่คนอื่นทำงานต่อได้
- แก้ปัญหาเทคนิคที่ยากที่สุดของกลุ่ม หรือแตกปัญหาให้คนอื่นแก้ได้
- รู้ว่าเมื่อไหร่ไม่ควรสร้างใหม่ และกล้าลดความซับซ้อนของระบบที่มีอยู่

**ยังไม่ถึงระดับนี้ ถ้า**

- ออกแบบระบบที่มีแค่ตัวเองเข้าใจ
- ผลักเทคโนโลยีใหม่โดยไม่คิดถึงคนที่ต้องดูแลต่อ

**หลักฐานที่ใช้ตอนประเมิน**

- RFC หรือ ADR ระดับข้ามทีมที่ถูกนำไปใช้
- ระบบที่เรียบง่ายขึ้นหลังการปรับ

**ถ้าอยากไปถึง**

- เลือกปัญหาเทคนิคที่กระทบหลายทีมหนึ่งเรื่อง เขียน RFC แล้วพาให้เกิดการตัดสินใจภายในไตรมาส

### L4 · การส่งมอบงาน

**สิ่งที่เห็นได้ในงานจริง**

- วางแผนงานที่กินเวลาหลายเดือนหรือหลายทีม และแบ่งเป็นช่วงที่ส่งมอบคุณค่าได้ทีละขั้น
- ปลด blocker ข้ามทีม และรู้ว่าต้องคุยกับใครเพื่อให้งานเดินต่อ
- ทำให้ทีมส่งงานได้ดีขึ้นในภาพรวม เช่น ลดเวลาตั้งแต่ commit จนถึง production

**ยังไม่ถึงระดับนี้ ถ้า**

- ส่งงานตัวเองได้ดีมาก แต่ทีมโดยรวมยังส่งงานช้าเท่าเดิม

**หลักฐานที่ใช้ตอนประเมิน**

- แผนงานหลายไตรมาสที่ทีมใช้จริง
- lead time หรือความถี่ในการ deploy ของทีมที่ดีขึ้น

**ถ้าอยากไปถึง**

- วัด lead time ของทีมตอนนี้ แล้วเลือกคอขวดหนึ่งจุดมาแก้ให้ได้ในไตรมาสนี้

### L4 · ขอบเขตและผลกระทบ

**สิ่งที่เห็นได้ในงานจริง**

- ขอบเขตคือทั้งทีมหรือหลายทีม และงานส่งผลต่อเป้าหมายของฝ่าย
- หาปัญหาที่สำคัญที่สุดเองโดยไม่ต้องมีใครมอบหมาย
- เชื่อมการตัดสินใจทางเทคนิคกับเป้าหมายธุรกิจ และอธิบายให้ผู้บริหารเข้าใจได้

**ยังไม่ถึงระดับนี้ ถ้า**

- ทำงานที่น่าสนใจทางเทคนิค แต่ไม่ได้ช่วยเป้าหมายของบริษัท

**หลักฐานที่ใช้ตอนประเมิน**

- โปรเจกต์ที่ริเริ่มเองและผลลัพธ์ทางธุรกิจที่ตามมา

**ถ้าอยากไปถึง**

- นัดคุยกับ product หรือ business lead เดือนละครั้ง เพื่อเข้าใจเป้าหมายของไตรมาส

### L4 · การทำงานร่วมกันและการสื่อสาร

**สิ่งที่เห็นได้ในงานจริง**

- สร้างความเห็นพ้องระหว่างทีมที่มีเป้าหมายต่างกัน
- สื่อสารการตัดสินใจทางเทคนิคได้ทั้งกับวิศวกรและผู้บริหาร โดยปรับรายละเอียดตามผู้ฟัง
- พูดเรื่องที่ไม่มีใครอยากพูดได้อย่างให้เกียรติ เช่น บอกว่าแผนนี้เป็นไปไม่ได้ พร้อมเสนอทางเลือก

**ยังไม่ถึงระดับนี้ ถ้า**

- ตัดสินใจคนเดียวแล้วประกาศ
- เกรงใจจนไม่พูดเรื่องความเสี่ยงสำคัญกับผู้ใหญ่

**หลักฐานที่ใช้ตอนประเมิน**

- การตัดสินใจข้ามทีมที่ทุกฝ่ายยอมรับ
- เอกสารที่ส่งถึงผู้บริหาร

**ถ้าอยากไปถึง**

- ฝึกเขียนสรุปการตัดสินใจหนึ่งย่อหน้าสำหรับผู้บริหาร คู่กับฉบับเต็มสำหรับวิศวกร

### L4 · การพัฒนาคนและภาวะผู้นำ

**สิ่งที่เห็นได้ในงานจริง**

- พัฒนา senior คนอื่นให้นำงานได้เอง
- สร้างวัฒนธรรมของทีม เช่น การ review การเขียนเอกสาร และการเรียนรู้จากความผิดพลาด
- ช่วย EM ประเมินและวางแผนการเติบโตของคนในทีม

**ยังไม่ถึงระดับนี้ ถ้า**

- ทีมพึ่งพาคนนี้จนถ้าลาพักร้อน งานหยุด

**หลักฐานที่ใช้ตอนประเมิน**

- senior ที่นำโปรเจกต์ได้โดยไม่ต้องให้คนนี้เข้าไปช่วย
- แนวปฏิบัติที่ทีมยังใช้อยู่แม้คนนี้ไม่อยู่

**ถ้าอยากไปถึง**

- ลาพักหนึ่งสัปดาห์โดยไม่เช็กงาน แล้วดูว่าอะไรติด สิ่งนั้นคือสิ่งที่ต้องส่งต่อ

### L4 · ความเป็นเจ้าของและมุมมองธุรกิจ

**สิ่งที่เห็นได้ในงานจริง**

- เป็นเจ้าของผลลัพธ์ของทั้งระบบ ไม่ใช่แค่ส่วนที่ตัวเองเขียน
- ลงทุนกับเรื่องระยะยาว เช่น ความปลอดภัย ความเสถียร และต้นทุน cloud ก่อนที่มันจะกลายเป็นวิกฤต
- ยอมรับความผิดพลาดจากการตัดสินใจของตัวเองอย่างเปิดเผย และพาทีมแก้

**ยังไม่ถึงระดับนี้ ถ้า**

- โยนความรับผิดชอบเมื่อการตัดสินใจทางเทคนิคไม่เวิร์ก

**หลักฐานที่ใช้ตอนประเมิน**

- แผนลดต้นทุนหรือเพิ่มความเสถียรที่เห็นผล

**ถ้าอยากไปถึง**

- ทบทวนการตัดสินใจทางเทคนิคเมื่อ 6 เดือนก่อน เขียนว่าอะไรถูก อะไรพลาด แล้วแชร์ให้ทีม

## L5 Principal Engineer

กำหนดทิศทางเทคนิคขององค์กรในระยะหลายปี การตัดสินใจส่งผลต่อรายได้ ต้นทุน หรือความเสี่ยงของบริษัทโดยตรง

ขอบเขต: ทั้งองค์กร

### L5 · ทักษะทางเทคนิค

**สิ่งที่เห็นได้ในงานจริง**

- กำหนดทิศทางเทคนิคระยะหลายปีขององค์กร และทำให้ทีมต่าง ๆ เดินไปทางเดียวกัน
- เป็นที่ปรึกษาในเรื่องเทคนิคที่ยากหรือเสี่ยงที่สุด และมักเห็นปัญหาก่อนคนอื่น
- ตัดสินใจเรื่อง build vs buy การเปลี่ยนแพลตฟอร์ม หรือการเลิกใช้ระบบเก่า ด้วยข้อมูลและความเข้าใจธุรกิจ

**ยังไม่ถึงระดับนี้ ถ้า**

- ความรู้ลึกมาก แต่ไม่ได้เปลี่ยนวิธีที่องค์กรสร้างซอฟต์แวร์

**หลักฐานที่ใช้ตอนประเมิน**

- technical strategy ที่เขียนและถูกนำไปใช้
- ระบบหลักที่เปลี่ยนไปตามทิศทางนั้น

**ถ้าอยากไปถึง**

- เขียน technical strategy หนึ่งหน้าสำหรับ 2–3 ปีข้างหน้า แล้วขอ feedback จากผู้บริหารและ staff engineer

### L5 · การส่งมอบงาน

**สิ่งที่เห็นได้ในงานจริง**

- ทำให้โปรแกรมงานขนาดใหญ่ระดับองค์กรสำเร็จ เช่น การย้ายระบบหลัก
- ออกแบบวิธีทำงานที่ทำให้หลายทีมส่งงานได้เร็วและปลอดภัยขึ้นพร้อมกัน
- รู้ว่าเมื่อไหร่ควรหยุดโปรเจกต์ และกล้าเสนอให้หยุด

**ยังไม่ถึงระดับนี้ ถ้า**

- ดูแลแค่โปรเจกต์ที่ตัวเองสนใจ

**หลักฐานที่ใช้ตอนประเมิน**

- โปรแกรมข้ามฝ่ายที่สำเร็จ
- โปรเจกต์ที่เสนอให้หยุด พร้อมเหตุผล

**ถ้าอยากไปถึง**

- เลือกโปรเจกต์ที่องค์กรกังวลที่สุด แล้วรับเป็นเจ้าของด้านเทคนิค

### L5 · ขอบเขตและผลกระทบ

**สิ่งที่เห็นได้ในงานจริง**

- ขอบเขตคือทั้งองค์กร หรือทั้งวงการในเรื่องที่เชี่ยวชาญ
- การตัดสินใจส่งผลต่อรายได้ ต้นทุน หรือความเสี่ยงของบริษัทในระดับที่ผู้บริหารวัดได้
- ช่วยให้บริษัทดึงดูดและรักษาวิศวกรเก่งได้ ผ่านชื่อเสียงทางเทคนิคหรือวัฒนธรรมทีม

**ยังไม่ถึงระดับนี้ ถ้า**

- ผลงานยังจำกัดอยู่ในทีมเดียว

**หลักฐานที่ใช้ตอนประเมิน**

- ผลกระทบทางธุรกิจที่อ้างอิงได้
- งานเขียนหรือการพูดที่คนนอกองค์กรอ้างถึง

**ถ้าอยากไปถึง**

- เข้าร่วมวางแผนประจำปีกับผู้บริหาร และรับผิดชอบส่วนเทคนิคของแผน

### L5 · การทำงานร่วมกันและการสื่อสาร

**สิ่งที่เห็นได้ในงานจริง**

- เป็นคู่คิดของผู้บริหารเรื่องเทคนิค และแปลงกลยุทธ์ธุรกิจเป็นแผนเทคนิค
- ทำงานกับฝ่ายอื่น เช่น กฎหมาย ความปลอดภัย การเงิน ในเรื่องที่มีผลต่อเทคนิค
- เป็นตัวแทนองค์กรกับคนภายนอกได้ เช่น partner หรือเวทีพูดด้านเทคนิค

**ยังไม่ถึงระดับนี้ ถ้า**

- สื่อสารได้ดีเฉพาะกับวิศวกรด้วยกัน

**หลักฐานที่ใช้ตอนประเมิน**

- แผนที่ทำร่วมกับฝ่ายอื่น
- การนำเสนอต่อผู้บริหารหรือภายนอก

**ถ้าอยากไปถึง**

- รับเป็นเจ้าของเรื่องเทคนิคหนึ่งเรื่องในการประชุมผู้บริหารไตรมาสถัดไป

### L5 · การพัฒนาคนและภาวะผู้นำ

**สิ่งที่เห็นได้ในงานจริง**

- พัฒนา staff engineer และ tech lead รุ่นถัดไป
- ร่วมกับฝ่ายบริหารกำหนดมาตรฐานการจ้างและการเติบโตของวิศวกร
- เป็นแบบอย่างของวัฒนธรรมที่องค์กรอยากได้ ทั้งความถ่อมตัวและการเรียนรู้

**ยังไม่ถึงระดับนี้ ถ้า**

- เป็นคนเก่งที่คนอื่นไม่กล้าเข้าหา

**หลักฐานที่ใช้ตอนประเมิน**

- คนที่ได้รับการพัฒนาจนก้าวขึ้นเป็น staff หรือ lead

**ถ้าอยากไปถึง**

- เปิดช่วงเวลาประจำให้คนในองค์กรจองคุยเรื่องเทคนิคหรือเรื่องอาชีพ

### L5 · ความเป็นเจ้าของและมุมมองธุรกิจ

**สิ่งที่เห็นได้ในงานจริง**

- รับผิดชอบความเสี่ยงทางเทคนิคขององค์กรในภาพรวม และทำให้ผู้บริหารเห็นภาพเดียวกัน
- ตัดสินใจเรื่องที่ยากและไม่เป็นที่นิยม เมื่อมันถูกต้องสำหรับระยะยาว
- คิดถึงผลกระทบต่อผู้ใช้ สังคม และกฎหมาย เช่น PDPA ในการออกแบบระดับองค์กร

**ยังไม่ถึงระดับนี้ ถ้า**

- เลี่ยงการตัดสินใจที่อาจผิด จนองค์กรไม่ได้เดินหน้า

**หลักฐานที่ใช้ตอนประเมิน**

- ทะเบียนความเสี่ยงทางเทคนิคที่ดูแลอยู่
- การตัดสินใจระยะยาวที่เวลาพิสูจน์แล้วว่าถูก

**ถ้าอยากไปถึง**

- ทำ risk review ด้านเทคนิคของทั้งองค์กรปีละครั้ง และเสนอแผนต่อผู้บริหาร

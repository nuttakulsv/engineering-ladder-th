# design review, RFC และ ADR

ทีมที่ไม่มีวิธีตัดสินใจเรื่องเทคนิคที่ชัดเจน จะตัดสินด้วยเสียงที่ดังที่สุดหรือคนที่อาวุโสที่สุด หรือไม่ตัดสินเลยจนงานค้าง เอกสารนี้คือวิธีที่ใช้ได้ในทีมขนาด 5–50 คน

## เมื่อไหร่ต้องเขียน

เขียน RFC (เอกสารเสนอการออกแบบ) เมื่อมีข้อใดข้อหนึ่ง

- เปลี่ยนแปลงที่ย้อนกลับยาก เช่น schema ของฐานข้อมูล API สาธารณะ การเลือกเทคโนโลยีหลัก
- กระทบมากกว่าหนึ่งทีม
- ใช้เวลาทำมากกว่าประมาณสองสัปดาห์
- มีทางเลือกที่คนในทีมเห็นต่างกันอย่างจริงจัง

ไม่ต้องเขียนสำหรับงานที่ย้อนกลับง่ายและอยู่ในทีมเดียว ให้ตัดสินใน PR หรือคุยกันใน chat ได้เลย

ส่วน ADR (Architecture Decision Record) คือบันทึกสั้น ๆ ว่าตัดสินใจอะไร เพราะอะไร มีทางเลือกอะไรบ้าง เขียนหลังตัดสินใจแล้ว เก็บไว้ใน repo คู่กับโค้ด เพื่อให้คนที่มาทีหลังรู้เหตุผล ถ้าอยากได้เครื่องมือช่วยจัดการ ADR และให้ PR เตือนเมื่อแก้โค้ดในส่วนที่มี ADR กำกับ ดู [decision-log](https://github.com/nuttakulsv/decision-log)

## โครงของ RFC

1. ปัญหาและเป้าหมาย สิ่งที่อยู่นอกขอบเขต
2. บริบทและข้อจำกัด เช่น เวลา ทีม งบ ระบบเดิม
3. ทางเลือกอย่างน้อยสองทาง รวมทาง "ไม่ทำอะไร" ถ้าเป็นไปได้
4. ข้อดีข้อเสียของแต่ละทาง เทียบในเรื่องเดียวกัน เช่น ความซับซ้อน ต้นทุน ความเสี่ยง เวลาที่ใช้
5. ทางที่เสนอ และเหตุผล
6. ความเสี่ยงและแผนรับมือ สิ่งที่ยังไม่รู้
7. ผู้ตัดสินใจ และวันที่ต้องได้คำตอบ

ความยาวที่ดีคือ 2–4 หน้า ถ้ายาวกว่านั้นมักเป็นเพราะเขียนรายละเอียดการ implement มากเกินไป

## การประชุม review

- ส่งเอกสารล่วงหน้าอย่างน้อย 2 วันทำการ และให้คอมเมนต์ในเอกสารก่อน
- ถ้ายังมีคนไม่ได้อ่าน ใช้ 10 นาทีแรกของประชุมให้ทุกคนอ่านเงียบ ๆ พร้อมกัน วิธีนี้ทำให้คนที่ไม่ถนัดพูดในที่ประชุมมีโอกาสคิดก่อน
- เริ่มจากคำถามที่ยังเปิดอยู่ ไม่ต้องเล่าเอกสารซ้ำ
- คนนำประชุมถามความเห็นจากคนที่ยังไม่ได้พูดโดยตรง โดยเฉพาะคนที่อายุงานน้อยกว่า ในวัฒนธรรมที่เกรงใจกัน ความเงียบไม่ได้แปลว่าเห็นด้วย
- จบด้วยหนึ่งในสามผล อนุมัติ อนุมัติพร้อมเงื่อนไข หรือต้องแก้แล้วกลับมาใหม่ ห้ามจบด้วย "ไปคิดกันต่อ" โดยไม่มีวันที่

## ใครเป็นคนตัดสิน

ตกลงกันไว้ก่อนว่าใครเป็นผู้ตัดสินของแต่ละเรื่อง ปกติคือ tech lead ของทีมเจ้าของระบบ หรือ staff engineer ถ้าข้ามทีม ผู้ตัดสินต้องฟังทุกฝ่าย แต่ไม่ต้องรอให้ทุกคนเห็นด้วย

หลังตัดสินแล้ว ใช้หลักเห็นต่างได้แต่ทำตามที่ตัดสิน (disagree and commit) คนที่ไม่เห็นด้วยบันทึกความเห็นไว้ใน ADR ได้ ถ้าภายหลังพบว่าทางที่เลือกไม่เวิร์ก ให้เขียน ADR ใหม่ที่แทนที่ฉบับเดิม ไม่ใช่ลบทิ้ง

## สัญญาณว่ากระบวนการหนักเกินไป

- คนเลี่ยงการเขียน RFC ด้วยการแบ่งงานให้เล็กลงจนไม่ต้องเขียน
- RFC รออนุมัตินานกว่างานที่จะทำ
- ประชุม review มีคนเข้าเกิน 8 คนเป็นประจำ
